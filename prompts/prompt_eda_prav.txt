2. src/data.py — требования к новому модулю
============================================================

Назначение: чистый модуль с переиспользуемыми функциями, который
импортируют eda.ipynb, evaluation.ipynb и будущий solution.ipynb.

Требования:
  - Чистые функции без print в теле, только return.
  - Docstring обязателен для каждой функции.
  - Зависимости: только pandas, numpy. Никаких sklearn / pyspark.
  - Никакой кириллицы в коде и комментариях.

Переносятся БЕЗ ИЗМЕНЕНИЙ ЛОГИКИ пять функций, которые сейчас
определены внутри eda.ipynb (в разделе D):
  build_overlap_pairs(views_frame, schedule_frame)
  build_airing_table(pair_frame, ratio_threshold=0.8)
  build_aggregated_items(pair_frame, ratio_threshold=0.8)
  items_for_weeks(pair_frame, views_frame, week_values)
Плюс две новые:
  items_for_weeks_with_ratio(pair_frame, views_frame, week_values, ratio_threshold)
  merge_overlapping_views(views_df)

Семантика merge_overlapping_views:
  Назначение: устранить двойной учёт просмотров, когда пользователь
  смотрит один канал с нескольких устройств. Пример из данных:
  у одного пользователя по шоу 2400480 total_watched_s = 2 276 062 с
  при сумме длин эфиров 569 100 с (ровно x4). Без склейки watched_s
  завышен, qualified_airings считает один и тот же эфир несколько раз,
  aggregate_ratio маскируется через min(watched_s, show_duration).

  Вход: DataFrame с колонками user_id (uint64), vsetv_id (int64),
        start_time (datetime64[ns]), stop_time (datetime64[ns]),
        duration (int64). Колонка iso_week может присутствовать —
        игнорировать.
  Выход: DataFrame с user_id, vsetv_id, start_time, stop_time, duration
         в тех же типах. iso_week не гарантируется, пересчитывается
         снаружи.
  Логика: для каждой пары (user_id, vsetv_id) объединить пересекающиеся
         интервалы [start, stop] в один: min(start), max(stop).
         Пересечение — когда start_next <= stop_prev и интервалы
         действительно перекрываются (полные дубли, вложенные, частичные).
         Касание концами (start_next == stop_prev) НЕ пересечение,
         два отдельных интервала.
  Производительность: векторизованно, без groupby.apply с циклом по
         пользователям. Ориентир — 5.8M строк views на 2 CPU < 30 сек,
         < 2 GB RAM (потолок окружения — 4 GB).

Обязательные юнит-тесты (внутри модуля, pytest-стиль, с skip-маркером
если pytest не установлен):
  - четыре копии одного и того же интервала → одна строка;
  - два частично перекрывающихся интервала → одна строка;
  - два интервала, касающихся концами → две строки;
  - три непересекающихся интервала → три строки.

4. outputs/evaluation/evaluation.ipynb — новый ноутбук
============================================================

Назначение: честная валидация. Никаких моделей — только три baseline
и MAP@5 на схеме, которая будет повторена на тесте.

Схема валидации:
  - история = недели 11–20;
  - target = недели 21–30;
  - пул кандидатов = уникальные tv_show_id != 0 из train_schedule_2
    (export_arh_21-30-final.parquet). Обоснование: на тесте кандидатов
    будет ограничивать test_schedule (31–42), поэтому на валидации
    эмулируем это же правило — без ограничения baseline берут шоу,
    которые в целевом окне не идут, и MAP искажается;
  - fallback единый для всех методов: глобальный топ-5 по популярности
    за историю, отфильтрованный пулом кандидатов. Никакие рекомендации
    не могут быть пустыми;
  - MAP@5: AP = sum_{i=1..5} (hits@i / i) / min(|gt|, 5).
    Пользователи с пустым gt исключаются из среднего и учитываются
    отдельным счётчиком n_users_eval.

Структура ноутбука (каждая ячейка — отдельный смысловой шаг):

     подзаголовок «## Evaluation setup» с описанием схемы выше.
